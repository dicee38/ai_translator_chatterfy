# ТЗ: AI-переводчик для Chatterfy (текст + голосовые + умный ответ)

Отдельный, самостоятельный проект — новое расширение, не часть
`Chat Summarizer`. Причина разделения: разные зоны ответственности и
разная чувствительность данных (статистика по лидам vs личная переписка
с живыми людьми) и разные права доступа — смешивать их в одном
расширении не стоит.

## 0. Цель и объём проекта

Три фичи, в порядке возрастания сложности и зависимости друг от друга:

1. **Перевод текста по выделению** — выделил кусок сообщения в чате →
   получил перевод на диалект собеседника во всплывающей плашке.
2. **Расшифровка + перевод голосовых** — кнопка на голосовом сообщении
   → текст на языке собеседника + перевод на русский.
3. **(Перспектива) Умный ответ** — кнопка рядом с полем ввода →
   модель предлагает ответ на диалекте собеседника + обратный перевод
   на русский для проверки оператором → оператор сам решает,
   вставлять/редактировать/отправлять. **Ничего не отправляется
   автоматически.**

Все три фичи — **read-only помощь оператору**, ничего не пишут в чат
и не меняют данные в Chatterfy сами.

## 0.1 Находка из HAR: API `messages/v1/search` — источник данных вместо DOM

Тот же паттерн, что уже сработал для Chat Summarizer: не нужно парсить
DOM переписки вообще — есть чистый API. Реальный ответ
`POST https://migration-api.chatterfy.ai/api/messages/v1/search`
(`{chat_id, limit}`) отдаёт полную историю чата, каждое сообщение:

```json
{
  "id": "01a0b40b-cfec-7138-bcb3-0f6477ffdb2b",
  "content": "",
  "sender_type": "incoming",   // incoming = собеседник, outcoming = оператор
  "sender": "",                 // uuid оператора, если outcoming
  "created_at": "2026-09-18T10:24:28.139605Z",
  "files": [
    {
      "type": "voice",
      "url": "https://prod-chatterfy-v1-files.s3-eu-central-1.amazonaws.com/contents/.../file_4819.ogg",
      "meta": { "duration": 27, "file_size": 575993 }
    }
  ]
}
```

**Следствия, меняющие план ниже:**

- `sender_type` — готовый, надёжный признак «это собеседник или
  оператор», вместо угадывания по CSS-классам в DOM. И контекст
  диалекта (Feature 1), и разметка диалога (Feature 3) строятся на нём.
- Текст сообщений — `content`, без парсинга DOM переписки вообще.
- Голосовые — не нужно искать `<audio>` в DOM: `files[].type === "voice"`
  сразу даёт прямую ссылку `files[].url` (`.ogg`, обычный S3-объект,
  отдаётся с поддержкой `Range`-запросов — качается обычным `fetch`)
  и `meta.duration` в секундах — **это закрывает п.10 «открытые
  вопросы» по DOM-пути голосового** и вдобавок даёт возможность
  показать оценку стоимости расшифровки (по длительности) ДО того,
  как оператор нажал «Перевести».
- Реальный пример из HAR показал важный нюанс для промпта перевода:
  собеседник иногда пишет диалект **латиницей** (марокканская дарижа
  в арабизи, например `"Khoya dir lia chi hal 3tini 50 eru..."`), а
  оператор отвечает литературным арабским в арабской графике. Промпт
  перевода должен ориентироваться не только на диалект/тон, но и на
  **систему письма** собеседника (латиница/арабица) — иначе перевод
  будет технически на нужном диалекте, но в непривычной для
  собеседника графике.

### 0.1.1 Уточнение по HAR: форма обёртки списка и порядок сортировки

Схема выше (п.0.1) — это форма ОДНОГО сообщения, она подтвердилась.
А вот форму верхнего уровня ответа (обёртку списка) изначально не
проверяли на реальном трафике и угадывали в коде расширения — угадали
неверно, из-за чего контекст диалекта Feature 1 на живой проверке
всегда приходил пустым (потрачено несколько раундов отладки, чтобы
докопаться). Подтверждено HAR-логом настоящего запроса от самого
Chatterfy (не от расширения):

```json
{
  "data": {
    "items": [ /* массив сообщений, схема как в п.0.1 */ ],
    "cursor": "01a0b422-2918-7394-8f39-e8e3af954a5c"
  }
}
```

Массив лежит по пути `data.data.items` (относительно всего JSON-ответа),
не `data.data` напрямую и не на верхнем уровне — предполагавшиеся
раньше варианты `[...]`/`{messages:[...]}`/`{items:[...]}` не
подтвердились, оставлены в коде расширения только как фолбэк.

**Порядок — от новых к старым** (первый элемент массива — самый
свежий), это тоже не было очевидно заранее и стоило отдельного бага
(код брал "последние N элементов массива", ожидая хронологический
порядок, а получал N самых старых сообщений в выборке).

**Пагинация — курсорная** (`cursor` в ответе, не `offset`/`page`).
`limit` в теле запроса, похоже, ни на что не влияет — сервер отдаёт
фиксированную страницу (на практике — 50 сообщений) независимо от
запрошенного числа. Для контекста диалекта (нужны последние 5-10
входящих сообщений) одной страницы с большим запасом достаточно —
**сознательно не реализовывали** проход по `cursor` за пределы первой
страницы, это не недосмотр, а решение под объём задачи. Если Feature 2
или Feature 3 когда-нибудь потребуют более глубокую историю — тогда
и добавить курсорную пагинацию, не раньше.

**Авторизация — третий и последний найденный кусок этой же цепочки
багов.** Эндпоинт НЕ открытый (первая гипотеза после неполного HAR
была именно такой и оказалась неверной — DevTools, судя по всему, не
включил заголовок авторизации в экспорт). Подтверждено сводным
`docs/chatterfy-api-reference.md` (справочник по обоим проектам,
основан на более полном разборе трафика): нужен заголовок
`authorization: <JWT>`, **без** префикса `Bearer`, токен ищется в
`localStorage`/`sessionStorage` страницы по виду (точное имя ключа не
зафиксировано). `credentials: 'include'` тут вообще ни при чём — это
не cookie-based авторизация, и она бы всё равно не сработала: сервер
отдаёт `Access-Control-Allow-Origin: "*"`, что несовместимо с
credentialed-запросом по спеке CORS.

Итого три причины бага "контекст диалекта пустой" были независимые
и накладывались друг на друга: неверный путь в ответе, неверный
порядок сортировки, отсутствие авторизации — чинили по одной,
подтверждая каждую реальным трафиком, а не одним предположением.

| Термин | Значение |
|---|---|
| Собеседник | Человек с другой стороны переписки (не оператор) |
| Диалект собеседника | Не литературный язык, а конкретный разговорный вариант, определяется по последним сообщениям собеседника в этом же чате |
| Оператор | Менеджер, который ведёт переписку через Chatterfy |
| Прокси / бэкенд | Свой маленький сервис, который держит API-ключи и вызывает внешние модели вместо расширения |

## 2. Архитектура целиком

```
┌─────────────────────────┐        ┌──────────────────────┐        ┌─────────────────┐
│  Content script          │  HTTPS │  Свой бэкенд-прокси    │  HTTPS │  OpenAI API       │
│  на v2.chatterfy.ai      │──────▶│  (Cloudflare Workers   │──────▶│  (транскрипция,   │
│                          │        │   или свой VPS)        │        │   перевод, умный  │
│  - ловит выделение       │        │                        │        │   ответ)         │
│  - ловит клики по голос. │        │  - держит API-ключ      │        └─────────────────┘
│  - рисует плашки         │◀──────│  - простая авторизация  │
│  - кнопка "умный ответ"  │  JSON  │  - лимит бюджета        │
└─────────────────────────┘        │  - НЕ логирует контент  │
                                    │    дольше необходимого  │
                                    └──────────────────────┘
```

**Почему не напрямую из content script в OpenAI:** ключ API нельзя
зашить в расширение — вытащат из исходников за 5 минут. Прокси
обязателен, это не опциональная часть архитектуры.

**Почему всё на OpenAI (транскрипция, перевод, умный ответ):** один
вендор — один ключ в прокси, один счётчик бюджета вместо двух. Для
транскрипции (speech-to-text) выбора и не было — это модель `gpt-transcribe`.
Для текстовых генеративных задач (перевод, умный ответ) — дешёвая
чат-модель OpenAI (см. `proxy/src/lib/pricing.js` — точное имя модели и
цену сверить перед реальным запуском, ориентир — доли цента за перевод).

## 3. Бэкенд-прокси

### 3.1 Эндпоинты

```
POST /translate
  body: { text: string, dialectContext: string[], targetLang?: string }
  → { translation: string }

POST /transcribe
  body: multipart/form-data, поле file (аудио .ogg/.oga)
  → { transcript: string, language?: string }

POST /suggest-reply   (этап 6, реализовано)
  body: { conversationContext: {role: "operator"|"interlocutor", text: string}[] }
  → { replyInDialect: string, backTranslationRu: string }
```

### 3.2 Авторизация прокси (обязательно, не опция)

Без этого — любой, кто найдёт URL прокси (например, открыв исходники
расширения), сможет дёргать его бесконечно и палить ваш бюджет API.

- Простой вариант: фиксированный секретный токен, зашитый в
  расширение и передаваемый заголовком (`X-Extension-Token`), прокси
  сверяет с известным значением на своей стороне.
- Риск: токен всё равно можно вытащить из расширения, как и API-ключ,
  но это ожидаемо и ограничивается следующим пунктом (бюджет), а не
  тем, что токен «не найдут».
- Не нужно городить OAuth/пользовательские аккаунты ради внутреннего
  инструмента для нескольких менеджеров — это избыточно для объёма
  задачи.

### 3.3 Бюджетный лимит (обязательно)

- Прокси считает суммарную стоимость запросов (по токенам/минутам
  аудио × актуальная цена модели) нарастающим итогом за день/месяц в
  простом хранилище (KV у Cloudflare Workers, или файл/таблица на
  VPS).
- При превышении заданного лимита (например, $5/день на старте,
  пока не откалибровали реальный расход) — прокси отвечает `429` с
  понятным телом ошибки, а не молча продолжает тратить.
- Расширение показывает это как отдельное состояние в UI
  ("дневной лимit на перевод исчерпан"), не как обычную сетевую
  ошибку — оператор должен понимать разницу.

### 3.4 Что НЕ хранит прокси

- Не логирует полный текст сообщений/расшифровок дольше, чем нужно
  для ответа на сам запрос (это переписка с реальными людьми —
  чувствительные данные, лишнее хранение — прямой риск).
  Исключение — агрегированная стоимость (для бюджета из 3.3), которая
  не должна включать сам контент.
- Не хранит аудиофайлы после того, как получена расшифровка.

### 3.5 Деплой

Два равноценных варианта, любой подходит — оба реализованы в коде:
- **Cloudflare Workers** (`proxy/workers/`) — бесплатный тариф с
  большим запасом (100k запросов/день, KV 100k чтений/1k записей в
  день) закрывает эту нагрузку с большим запасом. KV из коробки под
  бюджетный счётчик (3.3) вместо файла на диске, приём файла в
  `/transcribe` — нативный `request.formData()` (у Workers нет
  файловой системы, поэтому `multer` там не подходит). Перед первым
  `wrangler deploy`: `wrangler login`, `wrangler kv namespace create
  BUDGET_KV` (id — в `wrangler.toml`), `wrangler secret put
  EXTENSION_TOKEN`, `wrangler secret put OPENAI_API_KEY`.
- **Свой VPS/сервер** (`proxy/`, обычный Node/Express) — если уже
  есть готовая инфраструктура под другие проекты, разворачивается
  туда же как есть, файл на диске под счётчик.

## 4. Feature 1 — перевод по выделению

### 4.1 Поведение

1. Оператор выделяет текст сообщения собеседника (или свой, если
   нужно проверить, как звучит его реплика на диалекте).
2. Рядом с выделением появляется всплывающая плашка/кнопка.
3. По клику — плашка показывает "Перевожу..." → результат.
4. Кнопка "Копировать", кнопка "Вставить" (добавлена по запросу
   оператора — заменяет текущее содержимое поля ввода Quill переводом
   целиком, тем же приёмом execCommand из п.6.2), кнопка "Закрыть".
   Плашка не блокирует остальной интерфейс, закрывается кликом вне неё.

**Направление перевода — автоопределение (уточнено на живой проверке,
не было очевидно из исходной формулировки выше, и с первого захода
получилось неверно — см. ниже).** Изначально предполагалось, что
перевод всегда идёт "в диалект собеседника" — это верно, если выделили
СВОЙ черновик ответа. Но если выделить входящее сообщение собеседника
(уже на его диалекте), перевод "в диалект собеседника" — no-op
(буквально "с арабского на арабский", подтвердилось на реальном
Chatterfy).

Первая попытка фикса определяла направление по `sender_type`
сообщения, которому принадлежит выделенный текст: `incoming` → на
русский, иначе → в диалект. Тоже сломалось на живой проверке: обычный
рабочий цикл — перевести черновик в диалект, вставить, **отправить** —
и это отправленное сообщение лежит в истории как `outcoming`, но
ФАКТИЧЕСКИ уже на диалекте, не на русском. Повторное выделение такого
sent-сообщения снова давало "с дариджи на дариджу" — тот же баг, просто
с другой стороны.

Итоговое решение — определять направление не по тому, **кто** писал
(`sender_type`), а по тому, **на каком алфавите** написан сам
выделенный текст (`extension/content.js`, `detectDirection`): заметная
доля кириллицы → считаем текст русским (оператора) → перевод в
диалект; иначе (латиница/арабица/др.) → считаем, что текст уже на
диалекте → перевод на русский. Не требует сопоставления с историей
чата вообще.

### 4.2 Технически

```js
// ловим выделение
document.addEventListener('mouseup', () => {
  const sel = window.getSelection();
  const text = sel.toString().trim();
  if (!text) return hideBubble();
  const rect = sel.getRangeAt(0).getBoundingClientRect();
  showTranslateBubble(text, rect);
});
```

- Область слушателя — ограничить контейнером сообщений чата (не вся
  страница), чтобы не ловить выделение в сайдбарах/панелях.
- Контекст диалекта — 5-10 последних сообщений собеседника
  (`sender_type: "incoming"`, поле `content`) в текущем чате, через
  `POST /api/messages/v1/search` (см. п.0.1 — эндпоинт и схема уже
  подтверждены реальным трафиком).
- Промпт (пример, не единственно верный) — **обязательно учитывать
  систему письма** собеседника, не только слова: в реальной переписке
  из HAR (п.0.1) собеседник писал марокканскую дарижу латиницей
  (арабизи), а оператор отвечал литературным арабским в арабской
  графике — прямой перевод «на диалект» без учёта графики дал бы
  технически верный, но непривычный для собеседника текст:
  ```
  Вот последние сообщения собеседника (используй тот же диалект,
  стиль И систему письма — если он пишет латиницей/арабизи, а не
  арабской графикой, отвечай тем же способом):
  1. "..."
  2. "..."
  3. "..."

  Переведи следующий текст оператора на тот же диалект,
  сохраняя тон и уровень формальности:
  "<выделенный текст>"

  Ответь только переводом, без пояснений.
  ```
- Кэш — `Map` в памяти content script, ключ `hash(text + chatId)`,
  живёт на время открытой вкладки. Повторное выделение того же куска —
  без нового запроса.

### 4.3 UI-состояния плашки

- Загрузка (спиннер/текст "Перевожу...")
- Успех (перевод + кнопка копировать)
- Ошибка сети ("Не удалось перевести, попробуйте ещё раз")
- Бюджет исчерпан (см. 3.3) — отдельный текст, не как обычная ошибка

### 4.4 Альтернативный триггер — кнопка прямо в поле ввода (добавлено по ходу)

По запросу оператора, в духе DeepL: кроме выделения текста, есть вторая
точка входа в тот же перевод — маленькая кнопка (🌐) прямо в поле ввода
Quill (`extension/compose-translate.js`). Клик переводит то, что
оператор уже набрал, и **заменяет текст на месте** тем же
`document.execCommand('insertText', ...)` из п.6.2 (только сначала
выделяется всё содержимое редактора, потом вставка идёт поверх
выделения — не в курсор). Направление всегда `to_dialect` — это
заведомо черновик оператора, автоопределение по алфавиту тут не нужно.
Это не новая фича, а альтернативный UI для Feature 1: тот же
`/translate`, тот же бюджет, тот же переключатель "Feature 1" в
попапе. Кнопка позиционируется плавающей в углу поля ввода (не
встроена в панель инструментов Chatterfy — точное расположение внутри
их тулбара не подтверждено вживую, первая грубая версия).

## 5. Feature 2 — голосовые: расшифровка + перевод

### 5.1 Поведение

1. У каждого голосового сообщения в чате — небольшая кнопка "Перевести"
   (появляется при наведении, чтобы не захламлять интерфейс).
2. По клику — расшифровка (если ещё не делалась для этого сообщения)
   → перевод на русский, оба текста показываются в раскрывающемся
   блоке под самим голосовым (не всплывающая плашка — текста тут
   обычно больше, чем в коротком выделении).

### 5.2 Технически

- Список голосовых сообщений чата — не поиск `<audio>` в DOM, а тот же
  `POST /api/messages/v1/search` (п.0.1): фильтр `files[].type === "voice"`,
  ссылка на файл — `files[].url` (прямой S3-объект), длительность —
  `files[].meta.duration` в секундах, когда поле присутствует (бывает,
  что нет — не полагаться на него как на обязательное).
- **Поправка:** файл НЕ всегда `.ogg` — подтверждено на реальном трафике
  `.mp3` тоже (см. `docs/chatterfy-api-reference.md` §8). Расширение
  нужно брать из самого `files[].url`, не хардкодить `.ogg`.
- По этой длительности можно прикинуть стоимость расшифровки (секунды
  × цена/мин у `gpt-transcribe`), но **по запросу оператора это НЕ
  показывается** рядом с кнопкой «Перевести» — оценка стоимости в UI
  голосовых убрана, кнопка — просто «Перевести», без суммы. Изначально
  задумывалось как прозрачность для оператора, но на практике мешала
  больше, чем помогала (эту оценку раньше показывали).
- `fetch(files[].url)` → blob → отправить в свой прокси `/transcribe`
  (multipart) → получить транскрипт.
  **Важно (найдено на живой проверке этапа 1):** при отправке файла в
  OpenAI `/v1/audio/transcriptions` имя файла в multipart ДОЛЖНО
  содержать правильное расширение (`voice.ogg`/`voice.mp3`) — OpenAI
  определяет формат по расширению в имени, не по `Content-Type`; имя
  без расширения даёт `400 "Unsupported file format"` даже для
  валидного аудио. Также `gpt-transcribe` (реально
  `gpt-transcribe-api-ev3`) НЕ поддерживает `response_format:
  "verbose_json"` (только `json`/`text`) — значит `duration` из ответа
  транскрипции получить нельзя напрямую.
  **Исправлено (счётчик бюджета показывал в разы больше факта):**
  расширение теперь само передаёт в `/transcribe` поле
  `durationSeconds` — ту же реальную длительность из
  `files[].meta.duration`, что уже получена из Chatterfy API и
  показана в плеере. Прокси считает стоимость по ней
  (`estimateTranscribeCostUsdFromDuration`), а не угадывает по размеру
  файла — угадывание по размеру (`estimateTranscribeCostUsdFromFileSize`)
  осталось только фолбэком на случай, если длительность почему-то не
  передана. Заодно исправлена сама цена: $0.0045/мин (подтверждено
  официальным прайсингом OpenAI), не $0.05/мин — та цифра была
  методологической ошибкой калибровки на этапе 1 (поделили свою же
  оценку по размеру файла на реальную длительность, смешав две разные
  величины), а не просто устаревшей ставкой.
- Транскрипт → тот же пайплайн перевода, что в Feature 1 (с тем же
  контекстом диалекта — последние сообщения собеседника).

**Важно не спутать:** данные (URL, длительность) берутся из API, но
сама кнопка «Перевести» физически рисуется рядом с элементом
голосового сообщения в DOM — для этого всё равно нужно сопоставить
`message.id`/`files[].id` из ответа API с конкретным DOM-узлом плеера
на странице (например, по порядку сообщений или по видимому времени
на плеере). Это лёгкая DOM-привязка для позиционирования кнопки, а не
парсинг данных — сами данные DOM не парсит.
- Кэш **персистентный**, не только в памяти вкладки: голосовое
  сообщение не меняется, значит расшифровку можно закэшировать в
  `chrome.storage.local` по ключу `chatId + messageId` — не платить
  за повторную расшифровку при повторном открытии чата.

### 5.3 Качество распознавания — обязательный шаг ПЕРЕД остальной разработкой этой фичи

**Не писать код Feature 2, пока не прогнан ручной тест** (уже
согласовывали отдельно): 10-15 реальных голосовых на нужном диалекте
через `gpt-transcribe` без всякого кода — просто curl — и оценка на
глаз/носителем языка, разборчиво ли выходит и переживает ли смысл
последующий перевод. Если результат систематически плохой — вся
Feature 2 нецелесообразна в текущем виде, и это нужно понять ДО того,
как потрачено время на её реализацию, а не после.

### 5.4 UI-состояния

Те же четыре состояния, что в 4.3 (загрузка/успех/ошибка сети/бюджет),
плюс отдельное — "распознавание не дало разборчивого текста" (модель
может вернуть пустое/бессмысленное на сложном диалекте — это не
сетевая ошибка, показывать иначе).

## 6. Feature 3 (реализовано, было "перспектива") — умный ответ

Сделана после того, как Feature 1 и 2 подтвердили работоспособность
всей цепочки на реальном диалекте (условие §6.3 ниже выполнено) —
код, бэкенд-эндпоинт и UI готовы, задеплоено, проверено одним реальным
вызовом на проде. Живая проверка "нет случайной автоотправки" на
реальной странице (не только по коду) — ещё не делалась.

### 6.1 Поведение

1. Кнопка "Предложить ответ" рядом с полем ввода сообщения.
2. По клику — модель получает контекст последних N сообщений диалога
   (и от оператора, и от собеседника, с пометкой кто есть кто) и
   генерирует ДВЕ вещи одновременно:
   - ответ на диалекте собеседника;
   - обратный перевод этого ответа на русский — чтобы оператор понял,
     что он реально собирается отправить, не читая на диалекте.
3. Обе части показываются рядом, оператор:
   - жмёт "Вставить" — текст на диалекте попадает в поле ввода, дальше
     оператор редактирует/отправляет сам, как обычное сообщение;
   - либо жмёт "Отмена" — ничего никуда не вставляется.
4. **Автоотправки нет и не будет** — это осознанное архитектурное
   решение, не временное ограничение MVP.

### 6.2 Технически

- Контекст — то же `messages/v1/search`, последние N сообщений (число
  настраиваемое, стартовое значение — 10-15), с полем `sender_type`
  (п.0.1) для разметки, кто в диалоге оператор, а кто собеседник.
- **Поле ввода — не `<input>`/`<textarea>`, а редактор Quill**
  (`<div class="ql-editor" contenteditable="true">`) — это подтвердилось
  реальной вёрсткой композера сообщений, гадать на старте этапа больше
  не нужно. Значит трюк с `Object.getOwnPropertyDescriptor` для
  React-инпутов (для обычных полей) тут не подходит — Quill сам не
  React-controlled input в этом смысле, он слушает нативные события на
  contenteditable-узле. Рабочий путь:
  1. Кликнуть/сфокусировать `.ql-editor`.
  2. `document.execCommand('insertText', false, text)` — Quill
     перехватывает это как обычный ввод пользователя и сам обновляет
     свою внутреннюю модель (Delta), ничего дополнительно
     синхронизировать не нужно.
  3. Если `execCommand` в конкретной сборке Quill не подхватится —
     запасной путь: вставить текст напрямую в DOM (`.ql-editor`) и
     диспатчить `InputEvent('input', {inputType: 'insertText', data: text})`.
  Проверить конкретно на этой версии Quill — **быстрый ручной тест в
  начале этапа 6** (5 минут в консоли браузера), а не гадание вслепую,
  как было бы без этой находки.

### 6.3 Почему это отдельный этап, а не сразу вместе с остальным

Технически сложнее двух предыдущих фич (генерация связного ответа с
учётом диалога, а не перевод готового текста — больше простора для
неудачных генераций), и последствия ошибки модели тут выше (предложит
неуместный ответ оператору) — имеет смысл делать и обкатывать после
того, как Feature 1 и 2 подтвердили, что вся цепочка (прокси, бюджет,
качество перевода на конкретном диалекте) работает нормально.

## 7. Манифест и права

Новое расширение, `manifest_version: 3`, отдельно от Chat Summarizer:

```json
{
  "manifest_version": 3,
  "name": "Chatterfy AI Translator",
  "permissions": ["storage"],
  "host_permissions": [
    "https://v2.chatterfy.ai/*",
    "https://migration-api.chatterfy.ai/*",
    "https://<домен-вашего-прокси>/*"
  ],
  "content_scripts": [
    {
      "matches": ["https://v2.chatterfy.ai/*"],
      "js": ["translate-bubble.js", "voice-translate.js", "smart-reply.js", "content.js"],
      "run_at": "document_idle"
    }
  ]
}
```

`host_permissions` — узкий список конкретных доменов (не `<all_urls>`,
как было в Chat Summarizer) — этому расширению не нужен доступ ко
всему интернету, только к Chatterfy и своему прокси.

## 8. Приватность и данные

- Выделенный текст, расшифровки и контекст диалога — это реальная
  переписка с людьми (в т.ч. потенциально персональные данные). Прокси
  не хранит их дольше срока самого запроса (см. 3.4).
- В `chrome.storage.local` персистентно хранится **только** кэш
  расшифровок голосовых (5.2) — сами тексты переписки, но локально на
  машине оператора, не на внешнем сервере; если это неприемлемо для
  требований безопасности компании — этот кэш можно вообще убрать
  (ценой повторной оплаты транскрипции при каждом открытии чата).

## 9. Этапы (для Claude Code)

1. **Ручная проверка качества STT** (см. 5.3) — не код, до старта
   Feature 2. Этот пункт можно пропустить кодом, но не игнорировать:
   если результат теста плохой — Feature 2 нужно пересогласовать
   заново, а не реализовывать как задумано.
2. **Бэкенд-прокси, скелет.** `/translate`, `/transcribe`, авторизация
   по токену (3.2), бюджетный лимит (3.3), деплой на Cloudflare
   Workers (или VPS). Ручная проверка обоих эндпоинтов curl'ом до
   подключения расширения.
3. **Feature 1 целиком** — content script, выделение, плашка, контекст
   диалекта, кэш, все 4 UI-состояния (4.3).
4. **Feature 2 целиком** — детект голосовых, скачивание, `/transcribe`,
   прогон через тот же `/translate`, персистентный кэш, UI-состояния
   (5.4).
5. **Полировка** — настройки расширения (вкл/выкл фич, ручной выбор
   целевого диалекта на случай, если авто-контекст ошибся), индикатор
   остатка дневного бюджета в UI попапа.
6. **Feature 3 — сделано.** Контекст диалога, генерация
   ответ+обратный перевод, вставка в поле ввода (6.2), явное
   отсутствие автоотправки (по коду — «Вставить» вызывает только
   `insertIntoCompose`, никакого `submit`; живая проверка на реальной
   странице отдельным ручным тест-кейсом — ещё нет).
